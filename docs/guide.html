Practical workflow

Guide

This is the practical path for building real apps with Brackets. Start small, keep files clean, and let Datastar do the live frontend work underneath.

Start with this mental model

  • .view says what page exists.
  • .html says what the page looks like.
  • .logic says when the app does something.
  • .data says what the data is and how it behaves.
  • .api talks to shared authority and external systems.

Keep files small and clean

.view

Keep it declarative. Page id, route, html, layout, and named dependencies.

.html

Keep it presentational. Use Brackets syntax, but keep heavy logic out.

.logic

Keep it orchestration-first. Actions, route-aware flow, and lifecycle hooks.

.data

Keep it model-first. Validation, transforms, local queries, and persistence rules.

Build a fast SPA

Brackets supports both file-based and logic-based routing together. You can use lightweight .view routes for most pages and layer in router.logic or /routes/*.logic when the app needs stronger routing rules.

  • Layouts are preserved across same-layout route changes.
  • Route warming and prefetch are built in.
  • Route-target helpers keep router code cleaner than raw strings.

Build a local-first app

Put most or all model code in .data. Let the runtime or host manage .json, .yaml, and .db, then keep .logic focused on app behavior. 

// contacts.data
({
  async list({ storage }) {
    return storage.db('./contacts.db').query('select * from contacts order by name')
  }
})

Build a connected app

Use .api when you need shared authority, external services, or remote sync. The frontend file model stays the same, and Datastar-compatible HTTP and SSE remain the transfer path.

Move to production

Brackets is portable by design. The same app model can move from a desktop folder to a static server, Docker, or a paired backend without changing the public language.
